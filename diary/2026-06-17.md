# 2026-06-17

## OfferDetail bugfix: save-race + PDF preview re-render

User report after 2.34.0 hit production: "edit field content seems not to save, and it's unclear how to re-render the PDF."

Root cause analysis turned up two separate bugs sitting on top of each other:

### Bug 1 — local state wiped by refetch

The reset-from-server `useEffect` had every editable field in its dep array. Sequence that broke the user:

1. User types in field A → local state A="…"
2. Blur A → `saveAll` fires async (network roundtrip ~300ms)
3. While save is in flight: user moves to field B and starts typing → local state B="…"
4. Save resolves → `refetch()` → Apollo updates `data.offer` → useEffect re-runs because `offer.freeTextAfterItems` changed (it now matches what we typed in A) → state for ALL fields reset to server values → field B's in-progress edits wiped

Felt like "save doesn't stick" because the user's *next* save then sent the freshly-wiped state and overwrote A as well.

Fix: deps reduced to `[offer?.id]`. State only resets on navigation to a different offer, never on refetch of the same offer. Pattern is the same one the Apollo docs warn about ("don't drive controlled inputs from query data without an explicit lifecycle anchor").

### Bug 2 — PDF preview never re-fetched after save

Backend writes the regenerated PDF to the same `pdf_file` upload path (`offer-{number}.pdf`). The URL string returned from GraphQL is therefore identical before and after a save. The PDF-fetch `useEffect` was keyed on `[offer?.id, offer?.pdfUrl]` — same URL string → React skips the effect → iframe keeps showing the pre-save PDF. No bug from the backend's perspective; just a stale dep array on the frontend.

Fix: added a `pdfReloadToken` state counter that bumps after every successful `updateOffer` / `recreateOfferFromContract` / `finalizeOffer`. Added `?t={token}` cache-bust to the `/api/offers/:id/pdf/` request URL and put the token in the effect deps. The iframe now visibly reloads after each save.

### Dirty tracking + UX

Added `isDirty` boolean. Every editable onChange sets it true, every successful save sets it false. Side benefits:

- `saveAll` is a no-op when nothing is dirty (kills the spurious blur-save chatter)
- Save button is `disabled` when not dirty, visually `default` (blue) when dirty so the action that the user needs to take is obvious
- Amber "Ungespeicherte Änderungen" pill next to the button while dirty
- Hint text under the PDF preview: "PDF wird beim Speichern neu erzeugt" so users stop wondering why their typing didn't refresh the preview

### Decision: keep blur-save behavior, do NOT add live PDF preview

Considered debounced live PDF regeneration. Rejected — the PDF render is ~300ms server-side per call, the iframe-load is another ~200ms, and the user's typing cadence would queue dozens of redundant renders. Manual "save bumps PDF" matches the cost model and is now visually obvious thanks to the dirty pill.

### Lesson

Driving `useState` initial values from an async query is a footgun when the input is editable AND the query gets refetched. The reset effect dep array is the trap — it looks like "stay in sync with server" but actually means "race with the user." The correct anchor is "different entity loaded", not "any field changed."
