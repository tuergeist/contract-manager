## OfferDetail save: derived isDirty + first frontend tests

User reported the 2.34.1 fix wasn't enough: "after Save the 'Ungespeicherte Änderungen' pill briefly disappears then comes back". I spent a long time staring at the manual `setIsDirty(true/false)` flow looking for a setter race; I never reproduced it from code reading. So I shipped tests first, then refactored to derive state.

### Decision: drop the flag, derive isDirty

The old design held `isDirty` as a `useState` boolean and toggled it in two places: each editable field's `onChange` set it true, `saveAll`'s success branch set it false. Any race where local state and the flag drifted out of sync produced the symptom the user saw — e.g. an extra render cycle re-running an `onChange` with the same value would set the flag back to true with no real change behind it.

New shape: `isDirty` is a `useMemo` that compares the five local-state strings against the corresponding offer fields from the server. No flag, no setters. The only way `isDirty` can flip is if local-state or server-state actually differ. Refetch returning matching values → `isDirty` becomes false automatically; no manual reset needed in `saveAll`.

### New frontend tests: `OfferDetail.test.tsx` (7 cases)

First Vitest coverage for the offer detail page. Followed the existing `InvoiceDetail.test.tsx` Apollo-mocking pattern: `useQuery` returns from a `Map<querySubstring, result>`, `useMutation` returns spies keyed by mutation-name substring. Mocked `react-markdown` (ESM-only, breaks jsdom) and `SendOfferDialog` (touches unrelated GraphQL paths). Added `URL.createObjectURL` shim and a `fetch` mock for the PDF blob.

Tests cover:
- draft fields render editable
- Save button disabled until a field actually differs from the server
- typing fires `updateOffer` with the correct GraphQL input payload
- successful save (mock updates the query data in lockstep with the mutation resolve) → Save button disables itself again
- **race repro**: type A → save → type B → field B value is preserved (the 2.34.1 regression)
- server-side `success: false` → toast renders the error, button stays enabled for retry
- locked offer hides edit affordances + shows the locked banner + Copy-to-edit

### Local Vitest had to be unblocked first

`npx vitest` failed locally with `Cannot find module @rollup/rollup-darwin-x64`. Known npm-optional-deps bug. `npm install @rollup/rollup-darwin-x64 --save-optional` fixed it without reinstalling everything. Docker frontend container couldn't start at all (`no space left on device` on the docker volume) so the local path was the only option.

### Re: DevTools-blocked report

User also reported DevTools "not allowed" on the production domain. Searched the codebase: no anti-debug code, no CSP, no service worker. Only header from nginx is `X-Frame-Options SAMEORIGIN`, which has nothing to do with DevTools. Cause is browser-side — most likely a managed Chrome policy (`DeveloperToolsAvailability=DeveloperToolsDisallowed`, visible at `chrome://policy/`) or an extension. No app-side change needed; advised the user to check policy + test in Incognito.

### Pattern lesson

Controlled-component flags tracking "has the user touched anything" are a footgun whenever the input value is also driven from async query data. The clean version is always "is local state different from server state". Worth applying anywhere else in the app where similar patterns might exist (Invoice edit forms come to mind — not touched today, but on the watch list).

## Two more fixes on the same OfferDetail page

### iframe → object for the PDF preview

User reported Chrome DevTools auto-closing whenever they navigate to `/offers/:id`, AND refusing to open while on the page. Page-specific (other pages work). Searched the codebase: no anti-debug, no CSP. Smoking gun is the PDF preview `<iframe src={blobUrl}>`. Documented Chromium quirk: when an iframe loads content that PDFium takes over, DevTools can detach from the parent renderer and auto-close. Workaround is to render the PDF via `<object type="application/pdf" data=…>` instead. Same visual result, no DevTools detach. Added a `key={pdfBlobUrl}` so React unmounts the old `<object>` and mounts a fresh one when the blob URL changes (more reliable than mutating `data=` on the live element).

### saveAll was swallowing network/GraphQL errors

`await updateOffer(...)` had no try/catch. Network error or any throw inside Apollo (default `errorPolicy: 'none'` re-throws GraphQL errors) would silently reject the promise. From the user's point of view: click Save, nothing happens, no toast, no console log. Wrapped in try/catch with both a `console.error(...)` (so future debug sessions have evidence) and a visible error toast that includes the underlying message. Should make any further "save doesn't work" reports diagnose themselves.
