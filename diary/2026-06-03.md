## Imported Invoices: Storno + Credit-Note-Verknüpfung

User-Request: importierte Rechnung soll stornierbar sein (status: voided), optional sofort externe Credit Note/Memo zuordnen. Außerdem alternativ: importierte Credit Note nachträglich einer Rechnung zuweisen.

Entscheidung Design (nach User-Rückfrage):
- "voided gibts ja schon für selbst-erstellte rechnungen. das muss praktisch genauso" → Spiegel-Pattern aus `InvoiceRecord` für `ImportedInvoice`
- VOIDED in `ExtractionStatus` aufnehmen (statt separates Status-Feld), weil bestehender Enum schon Lifecycle-Stati (CONFIRMED/SENT/PAID) hat
- Neuer `DocumentType` Enum (INVOICE/STORNO), neue Felder `storno_of`, `void_reason`, `voided_at`, `voided_by`

Backend (`apps/invoices/models.py` + Migration `0028_importedinvoice_document_type_and_more`):
- ExtractionStatus.VOIDED ergänzt
- DocumentType TextChoices analog InvoiceRecord
- `storno_of` selbst-FK, `void_reason`, `voided_at`, `voided_by` (FK User)
- Properties `is_voided`, `is_credit_note`
- Index auf `(tenant, document_type)`

GraphQL (`apps/invoices/schema.py`):
- `InvoiceType` um Void-/Credit-Note-Felder erweitert: `document_type`, `void_reason`, `voided_at`, `voided_by_name`, `storno_of_id`, `storno_of_number`, `credit_note_id`, `credit_note_number`
- `_convert_imported_invoice` liefert reverse-Lookup über `inv.storno_records.order_by("-created_at").first()` für `credit_note_*`
- Vier neue Mutations:
  - `voidImportedInvoice(invoiceId, reason, creditNoteId?)` — setzt voided, optional verlinkt vorhandene Credit Note in einer Transaction
  - `unvoidImportedInvoice(invoiceId)` — rollback, restored auf PAID (wenn payment_matches) oder CONFIRMED, unlinkt alle storno_records
  - `linkImportedCreditNote(creditNoteId, targetInvoiceId, reason)` — markiert Source als STORNO + setzt Target auf voided (für "nachträglich zuweisen"-Pfad)
  - `unlinkImportedCreditNote(creditNoteId, keepTargetVoided=false)` — entkoppelt, optional bleibt Target voided

Frontend (`ImportedInvoiceDetail.tsx`):
- Drei neue Action-Buttons im Header:
  - "Stornieren" (rot outline) für non-voided non-credit-note Invoices in {extracted, confirmed, sent, paid}
  - "Storno aufheben" (RefreshCw) für voided Invoices
  - "Als Gutschrift zuordnen" für non-voided non-credit-note (für Credit-Note-First-Pfad)
- Status-Banner-Card oberhalb des Grids:
  - Voided → amber, zeigt void_reason + voided_at + voided_by + verlinkte Credit Note (oder "keine verknüpft")
  - Credit Note → lila, zeigt Storno-Target-Rechnung + Unlink-Button
- Zwei neue Dialoge:
  - Void-Dialog: required reason + optionaler Searchable-Picker für existierende Imported Invoice als Credit Note (debounced 250ms gegen `invoices(search:)` Query)
  - Link-as-Credit-Note-Dialog: Picker für Target-Rechnung (excludiert sich selbst + bereits-stornos) + optional reason
- `ExtractionStatusBadge` um `voided`-Case erweitert (grau line-through)

Tests: `backend/tests/test_imported_invoice_void.py` (9 Tests, alle grün): void → marks voided, rejects empty reason, links credit note in same call, double-void rejected, link self-rejection, unlink restores target, unlink-keep-voided, unvoid restores. Vollständige Invoice-Suite (62 passed, 4 skipped). Frontend tsc clean.

Translation-Keys ergänzt: `importedInvoiceDetail.void*`, `*CreditNote*`, `markAsCreditNote`, `linkAsCreditNote*`, `voidReason*` in de + en.

Design-Discovery: Reverse-Lookup über `storno_records.first()` reicht für aktuellen Use-Case, aber wenn mehrere Credit Notes pro Invoice nötig wären, müsste das ein Array werden. Für jetzt: 1:1 (Pattern matched self-issued Storno).

## Imported Invoices: invoice_date als Sent-Date + Backfill

User-Request: importierte Rechnungen haben ein `invoice_date` — dieses Datum repräsentiert das Versanddatum. ExtractionStatus.SENT existiert bereits im Enum, wurde aber nirgends gesetzt (außer als Revert-Ziel beim Entfernen einer Zahlungszuordnung).

Decision: SENT bedeutet ab jetzt "issued/sent to customer". Imported Invoice mit invoice_date → SENT statt CONFIRMED.

Backend (`apps/invoices/schema.py`):
- Neue Helper-Funktion `_active_status_for_imported(inv)` — Priority PAID > SENT > CONFIRMED
- An vier Stellen verwendet:
  - `confirm_invoice` Mutation (Standard-Bestätigung)
  - `confirm_extracted_invoice` Mutation (mit user-overridden Feldern)
  - `unvoid_imported_invoice` (Restore nach Storno)
  - `unlink_imported_credit_note` (Restore nach Credit-Note-Detach)
- Voher: hartcodiert `CONFIRMED if not payment_matches else PAID` — dieser Code verlor die SENT-Stufe

Backfill-Migration `0029_backfill_imported_invoice_sent_status` (RunPython, reversible):
- Forward: `extraction_status IN (extracted, confirmed) AND invoice_date IS NOT NULL AND document_type='invoice'` → SENT
- Reverse: SENT ohne payment_match → CONFIRMED (EXTRACTED-Distinction geht verloren, akzeptiert)
- Voided + Credit Notes ausgeschlossen

Datenwirkung lokal: 131 von 134 Rows promoted (3 EXTRACTED behielten Status — kein invoice_date extrahiert). Original-Verteilung: 133 extracted / 380 paid / 1 sent / 1 duplicate. Nach Backfill: 3 extracted / 380 paid / 131 sent / 1 duplicate.

Diskussion: erste Variante der Migration enthielt nur CONFIRMED → SENT (0 Rows betroffen, da auf dieser Datenbank die meisten Rows nie das Review-Gate passierten und direkt EXTRACTED→PAID via auto-payment-match laufen). Verbreitert auf EXTRACTED|CONFIRMED, weil User-Intent klar war: "ein PDF mit Datum wurde definitiv schon versendet".

Tests: 2 neue Tests in `test_imported_invoice_void.py::TestSentDateLifecycle` (confirm mit/ohne invoice_date), bestehender unvoid-Test verifiziert SENT-Restore. 11/11 grün.

Kein Release-Tag — User-Iteration läuft.
