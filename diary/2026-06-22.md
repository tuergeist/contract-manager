# 2026-06-22

## Clockodo API v2 → v3 migration

User report: "Failed to create one-off project '[…]': Clockodo POST /projects returned 410: 'This API version has been deprecated and is no longer available. Please upgrade to the latest version.'"

Cause: Clockodo retired API v2 in mid-2026. POST endpoints on v2 now return 410. GET endpoints on v2 still answered (probed live and got 401 instead of 410 for unauthenticated requests on both v2 and v3), but only as a grace period — full removal is the announced direction. So a partial migration would leave us blind: read-side works, write-side breaks at runtime.

Fix: bumped `ClockodoProvider.API_BASE` from `https://my.clockodo.com/api/v2` to `https://my.clockodo.com/api/v3`. All five endpoints we use (`aggregates/users/me`, `absences`, `entrygroups`, `customers`, `projects`) are available on v3 with identical paths and payload shapes per https://www.clockodo.com/en/api/. No callsite changes needed inside the provider.

### Why the tests didn't catch this

Existing `test_clockodo_provider_pacing.py` and `test_clockodo_provisioning.py` mock `httpx.request` so they never see the real Clockodo response. They're invaluable for verifying retry/backoff and our payload shape, but they can't detect upstream deprecations or schema drift.

### Live contract tests — discussed, deferred

Proposed a live env-gated contract-test layer (skip when `CLOCKODO_API_*` not set, run on demand via Make target, hit GET endpoints only so no side effects). User chose to defer. Worth revisiting if Clockodo bumps the version again — the cost of a 5-minute deprecation script is much smaller than next debug round-trip.

### Verification

Reproduced the failure mode by reading the user's exact 410 message into the diff context. Bumped to v3, ran the full backend suite (1525 passed, 4 skipped), no regressions because the mocks don't pin the version path. Manual confirmation against the actual v3 endpoint will happen on the next user-facing "create one-off project" action in production after deploy.
