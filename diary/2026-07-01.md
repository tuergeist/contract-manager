## Auftragsbestätigung: MwSt. nach Kundenland (2.34.12)

Bug: Auftragsbestätigungen (OCs) berechneten immer den Tenant-Standardsatz (19%), unabhängig vom Kundenland — auch für Nicht-VAT-Länder.

Ursache: `OrderConfirmationService` ignorierte Land/VAT-Klassifizierung komplett und nutzte stur `default_tax_rate`. Rechnungen und Angebote machen das längst richtig über gemeinsame Helper in `apps/invoices/services.py`.

**Behoben:** `build_template_context` nutzt jetzt `_classify_customer` + `_get_vat_sentence` aus `apps.invoices.services`:
- inländisch (Firmenland == Kundenland) → Standardsatz (19%)
- EU → 0% + Reverse-Charge-Hinweis
- Drittland → 0% + Ort-der-Leistung-Hinweis

Template (`order_confirmation.html`): Steuerzeile nur noch `{% if not vat_sentence %}`, sonst wird der konfigurierbare Hinweis (`vat_text_eu` / `vat_text_non_eu` aus `CompanyLegalData`) gerendert — identisch zur Rechnung. Fallback-`company`-Dict um die vat_text-Keys ergänzt, damit `_get_vat_sentence` auch ohne `CompanyLegalData` greift.

Entscheidung: bewusst die vorhandenen Invoice-Helper wiederverwendet statt eigener Logik — eine Quelle der Wahrheit für die VAT-Klassifizierung.

## Hinweis auf neue Version (2.35.0)

Installierte Instanzen sollen erkennen, wenn im öffentlichen Repo ein neuerer Release-Tag existiert, und das oben als grüne Zeile anzeigen — verlinkt aufs Changelog.

**Architektur-Entscheidungen:**
- **Backend-Proxy statt Client-Fetch:** GraphQL-Feld `CoreQuery.latestVersion` holt den höchsten Semver-Tag via GitHub Tags-API und cached ihn 1h in Redis. Grund: ein zentraler, gecachter Abruf statt pro-Browser — bleibt weit unter dem unauth Rate-Limit (60/h pro IP → ~24/Tag). Fällt bei Offline/Rate-Limit still auf `None`, damit das Frontend einfach kein Banner zeigt statt einen Fehler.
- **Version-Quelle:** Tags sind die Wahrheit (kein `v`-Prefix). Frontend kennt seine eigene Version über `VITE_BUILD_VERSION` (Docker-Build-Arg, `Dockerfile.prod`). Lokal ist das `dev` → nicht parsebar → Banner erscheint im Dev nie, nur in gebauten Images.
- **Link-Ziel:** GitHub-Tags-Seite, nicht die In-App-`/about`-Seite. Grund: die installierte App bündelt nur das Changelog vom Build-Zeitpunkt — die neue Version fehlt dort. GitHub zeigt immer den aktuellen Stand.
- **Dismiss:** pro Version in `localStorage`; beim nächsten Release erscheint das Banner wieder.

Neue Files: `apps/core/version_check.py`, `lib/versionCheck.ts`, `components/UpdateBanner.tsx`. Banner sitzt in `Layout.tsx` als Vollbreite über der Sidebar/Main-Zeile (Root auf `flex-col` umgestellt).

Tests: Backend `test_version_check.py` (9), Frontend `versionCheck.test.ts` (8) — Semver-Parsing, max-Tag, Cache, Fehler→None.

## Auftragsbestätigung erneut senden (2.35.1)

Nach dem PDF-Neu-Erzeugen (`OrderConfirmationDetail`) gab es keinen Sende-Button, und `send_order_confirmation` blockt hart bei `status==SENT` (`"already sent"`).

**Entscheidung:** dedizierte Mutation `resendOrderConfirmation` statt den bestehenden SENT-Guard aufzuweichen. Grund: Erst-Versand (ContractDetail-Dialog, der jeweils einen neuen Draft anlegt) bleibt geschützt; nur die explizite Resend-Aktion umgeht den Guard. Der Send-Service selbst hat keinen internen Guard — er sendet und überschreibt `sent_at`/`sent_to`/`status` jedes Mal, also greift Resend ohne weitere Änderung.

Button sitzt bewusst auf der OC-Detailseite (Landing nach Regenerate), nicht in ContractDetail. Label statusabhängig: „Senden" (Entwurf) bzw. „Erneut senden" (`sentAt` gesetzt), mit `window.confirm` vor dem Resend.

Tests: `test_order_confirmation_resend.py` (3) — Resend trotz SENT, not-found, RBAC (Viewer abgelehnt). Task via `.delay` gemockt.
